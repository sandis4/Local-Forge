## 1. Выбор модели без автозапуска

### Что было
Выбор модели в меню чата сразу отправлял `load` в движок. Поменять
контекст, потоки, KV-кэш или адаптер до загрузки было нельзя.

### Что стало
- Выбор модели только запоминает её и переводит чат в состояние `Unloaded`.
- Старый движок при смене модели гасится, чтобы статус `Ready` не относился
  к уже другой модели и чтобы освободить RAM.
- В строке композера появляется кнопка **«Загрузить модель»**.
- В диалоге **«Параметры»** по-прежнему есть кнопка «Загрузить модель» —
  можно сначала поменять настройки, потом загрузить.
- Хаб → «Использовать модель» идёт через тот же путь (`Chat::select_model`).
- Пока идёт загрузка/генерация/агент, смена модели игнорируется.

### Файлы
- `src/chat.rs` — `select_model()`, `unload()`, кнопка загрузки.
- `src/gui.rs` — хаб использует `select_model()`.
- `src/i18n.rs` — подсказка «Выбери модель сверху.»
- тест `selecting_model_waits_for_explicit_load`.

## 2. Экспериментальный ленивый режим MoE (Gemma 4 E2B и подобные)

### Идея
Для MoE-моделей не держать в RAM веса всех экспертов, а читать с SSD
только те, которые реально вызываются роутером. После каждой генерации
страницы экспертов выгружаются из процесса — следующая генерация снова
читает их с диска.

**Это сознательно экспериментальный режим:** он очень сильно нагружает SSD
и CPU (page faults + повторное чтение safetensors). Цель — проверить сам
подход; нормальная реализация (ленивые модули экспертов, аккуратный
per-expert LRU-кэш) — отдельная задача.

### Как включить
**Настройки → Чат → «MoE: грузить только используемые эксперты (эксперимент)»**
или в чате: **Параметры → тот же чекбокс**. Оба места меняют одно значение
и сохраняют его.

Настройка сохраняется в `%APPDATA%\LocalForge` (`chat_moe_lazy`).
Применяется при следующей загрузке модели. Для GGUF-моделей не действует:
там работает llama.cpp со своим mmap.

### Что происходит технически
1. GUI передаёт в `chat_engine.py` команду `load` с полем `"moe_lazy": true`.
2. `TransformersBackend` передаёт флаг в `model_loader.load_model_auto(..., moe_lazy=True)`.
3. Загрузчик проверяет конфиг (`num_experts`, `num_local_experts`,
   `n_routed_experts`, `moe_intermediate_size` и т.п.).
4. Если это MoE:
   - модель **принудительно** грузится через mmap (даже если веса влезают в RAM);
   - 4-bit GPU-путь (bitsandbytes) отключается — он несовместим с ленивой подкачкой;
   - запоминаются тензоры экспертов (по именам `experts` / `moe`).
5. После каждой генерации вызывается `trim_expert_pages(model)`:
   - **Linux/macOS** — `madvise(MADV_DONTNEED)` по диапазонам экспертных
     тензоров. Они file-backed из safetensors, поэтому при следующем
     обращении читаются заново с диска.
   - **Windows** — `EmptyWorkingSet` для процесса (грубее: выгружает
     рабочий набор целиком, не только экспертов).
6. В `info` события `ready` добавляется `moe_lazy: true`; в лог идёт
   предупреждение о нагрузке.

### Ограничения (важно)
- Если архитектура считает экспертов **группой** (один batched-matmul по всем
  экспертам, как в некоторых реализациях Mixtral), роутер всё равно трогает
  все веса — выигрыша по RAM не будет, будет только оверхед.
- Windows-ветка (`EmptyWorkingSet`) выгружает весь рабочий набор процесса,
  а не только экспертов; это ещё медленнее.
- Режим не используется при обучении (trainer грузит модель без `moe_lazy`).
- Нет гарантии, что ОС не вернёт страницы в RAM раньше времени.
- Работает только с safetensors-моделями (transformers), не с GGUF.
- Возможны падения на экзотических архитектурах: режим помечен экспериментальным.

### Файлы
- `python/model_loader.py` — `_is_moe_config()`, `_expert_tensors()`,
  `trim_expert_pages()`, параметр `moe_lazy`, принудительный mmap.
- `python/chat_engine.py` — `TransformersBackend(moe_lazy=...)`, вызов trim
  после генерации, парсинг `moe_lazy` из команды `load`.
- `src/chat.rs` — поле `moe_lazy`, передача в `load`.
- `src/settings.rs` — `chat_moe_lazy`.
- `src/gui.rs` — чекбокс и предупреждение в настройках, применение к чату.
- `src/i18n.rs` — RU/EN строки.

### Что дальше (кандидаты)
- Ленивые модули экспертов с LRU-кэшем (без глобального `EmptyWorkingSet`).
- Точный `madvise` только по страницам экспертов и на Windows
  (`OfferVirtualMemory` / `VirtualUnmap`).
- Учёт реального top-k роутера, чтобы не выгружать только что использованные
  эксперты слишком агрессивно.
- Отдельный профиль «беречь RAM / беречь SSD».
